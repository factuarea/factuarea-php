# ResolveStorefrontPriceRequest

Resolve what a shopper would pay for ONE selection, with the same pricing engine the merchant uses. The body carries the complete selection — `product_id` required, plus `variant_id`, `presentation_id`, `configuration_id`, `selection_signature` and `options` as a list of pairs of `group_id` and `value_id` — and `quantity`, which is required, greater than zero and with at most four decimals. There is NO price-list field: the rate applied is the one the shop declares for its storefront and the server resolves it, because being able to propose it from the browser would be being able to choose the price. You get back the unit price, the currency, the unit that price refers to, the applicable tax and the line total; what you deliberately do NOT get is which price list won, the source amount or the breakdown of option adjustments, which are commercial data of the seller. Read the result as a PREVIEW: the amount an order line freezes is resolved again when the order is created, and any amount sent in a body is ignored. It stores nothing. A reference of another shop is rejected exactly like one that does not exist, and a field this operation does not know is rejected naming it.
