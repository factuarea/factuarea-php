# ResolveStorefrontCatalogSelectionRequest

Ask whether what a shopper has chosen CAN BE OFFERED, before asking for its price and before putting it in a cart. The body carries the COMPLETE selection: `product_id` is required, and `variant_id`, `presentation_id`, `configuration_id`, `selection_signature` and `options` travel when the shopper has already chosen them. `options` is a list of PAIRS of `group_id` and `value_id` — one value per group, at most 50 — and never a flat list of values, so the same choice cannot be written in two ways. Sending the configuration AND the cross that produces it at the same time is legitimate here: a cart line holds both, so checking one again resends both. A combination that cannot be offered is NOT an error of the request: it comes back with 200 saying so and why, because the rejection belongs to the operations that CONFIRM — the cart and the order — and this one exists precisely so a storefront can warn before. It stores nothing. Every reference is checked against the shop that owns the key, and one of another shop is rejected exactly like one that does not exist; a field this operation does not know is rejected naming it, because a selection written with the vocabulary of another operation would otherwise be answered as if it were this one.
